# known-good 앵커 보관 (JUDGMENT_V1.1 §3.12.3 / §3.11)

스텝이 **실측 완료조건을 통과**하면 그때의 바이너리를 여기 보관한다.
빌드만 통과한 것은 앵커가 아니다 — 실측 통과분만 넣는다.

## 앵커가 뭔가 (git 이 있는데 왜 따로 두나)

**git 은 소스를 되돌리고, 앵커는 바이너리를 되돌린다.**
소스를 되돌려 다시 빌드해도 같은 바이너리가 나온다는 보장이 없다 —
Studio SDK 버전, `autogen/` 재생성(**핀 설정이 되돌아간 사고 실제 발생**),
Studio 소유 `config/` 헤더 때문이다.
앵커는 **그때 실제로 동작한 바로 그 바이트**다. Commander 로 바로 플래시하면
빌드 없이 30초에 그 시점으로 복귀한다.
→ 회귀 시 **"하드웨어냐 코드냐"를 재빌드 없이 가르는 도구**.

## 보관 방법 (2026-09-07~ Claude 가 직접 수행)

★소장이 빌드·실측을 마치면 **Claude 가 앵커 생성까지 처리한다.** 넘기지 않는다.

```
cp "NetAnalyzer_FG23_V01/GNU ARM v12.2.1 - Default/NetAnalyzer_FG23_V01.s37" \
   "_known_good/S<N>_<YYYYMMDD>.s37"
```

**★복사 전 반드시 검증** — 실측한 바이너리가 아닌 걸 앵커로 두면 의미가 없다:
1. 빌드 `.s37` 의 mtime 이 소스(`*.c/*.h`) mtime 보다 **뒤**인가
2. 빌드 이후 소스가 바뀌었다면 **주석만 바뀐 건지** 확인
   `git show <커밋> -- <파일> | grep -E "^[+-]" | grep -v "^[+-][+-][+-]" | grep -vE "^[+-] \*"`
   → 비어 있으면 주석만 = 바이너리 동일
3. 매크로(`FS_*`) 가 실측 당시 값과 같은가

그리고 같은 커밋에:
- 아래 "보관 이력" 표에 1줄
- `step_config.h` 하단 "실측 이력"에 결과 1줄
- **결함이 남아 있는 앵커는 결함을 명시**한다 (예: "연속 수신 안 됨")

## 회귀 발생 시 (§3.11)
1. 원인 구간 명확 → 타겟 패치
2. 원인 불명 → `step_config.h` 의 `FS_N` 을 낮춰 baseline 복귀 후 bisection
3. 추측 패치는 30분·3회 time-box, 안 되면 baseline 복귀
4. 여기 보관된 `.s37` 을 Commander 로 직접 플래시하면 즉시 그 시점으로 복귀

### ⚠ 이 앵커의 한계 (결함 명시)

1. **영점 미확정 — 약 +40 mA 상당.**
   무부하(배터리 단독, 디버거 분리)에서 `+32 mA`(`raw 0020`)가 읽혔다. 그때 보드는
   방전 중이었으므로 참값은 음수이고, 따라서 오프셋은 **32 mA 보다 크다**(+37~52 mA 추정).
   데이터시트 입력 오프셋은 ±50~100 µV(= ±5~10 mA)라 **규격의 3~6배**다.
   CMRR(최소 120dB → 12V 에서 12µV)로는 설명되지 않는다 → 원인 미규명.
   → **0.3 A 미만 판정에 쓰지 말 것.** 0.3~2 A 에서는 오차 1% 안쪽.
2. **§5-2(무부하 ±수 mA)는 이 하드웨어로 달성 불가.**
   R33 10mΩ + 데이터시트 오프셋 ±5~10 mA 이므로 부품 규격보다 엄격한 요구다.
   기준을 ±10 mA 로 완화하거나 항목을 재정의해야 한다. **소장 판단 대기.**
   ※ 2026-10-16 소장 판단: *"지금은 저전류를 잴 필요 없다. 충전전압·배터리전압·
     저전압을 1% 이내로 재는 것이 목적이니 이 정도 오차는 인정한다."* → 수용.
3. **전압 정확도는 부품 규격상 상온 ±0.5% / 전온도 ±1%.**
   1% 요구의 **경계선**이다. `BAT_CRITICAL` 9.0V 판정 시 실제 차단점이
   8.91~9.09V 로 흔들릴 수 있다(BMS 8.4V 까지 600mV 여유 → 안전측 문제없음).
   → **DMM 으로 팩 전압 1회 대조**하면 이 개체의 실제 게인오차가 확정된다. 권장.
4. **`.slcp` 정리의 효과는 미검증.** 헤더가 재생성되지 않아(기존 파일 보존)
   새로 넣은 921600/NONE/1024 가 올바른 헤더를 만드는지 아직 확인 못 했다.
   검증하려면 헤더를 지우고 Force Generation 해야 하며, 실패 시 UART 가 죽는다 → **별건**.
5. **TYPE='B' 프레임 송신 없음** — S11b 범위. 지금은 사람이 읽는 로그까지만.
6. **워치독 실제 물림(T6) 여전히 미확인** (S14a+e 앵커에서 이어진 한계).
7. **로그 형식이 다르다 — `t=…ms` 가 안 찍힌다.**
   앵커를 뜬 뒤 `ina219.c` 1Hz 줄에 타임스탬프를 추가했다(§5-10 창 측정용).
   기능·측정값은 동일하다. **타임스탬프가 필요하면 `S11a_20261016_tstamp.s37`** 를 써라.

### 메인루프 전제 변경
`작업정리_S14a_S14e §3` 이 *"블로킹 구간 없음"* 을 근거로 워치독 2.05초를 잡았다.

### 왜 따로 두나

**§5-10 창 측정(실장비 방전 9.11시간)을 실제로 돌린 바이너리가 이것이다.**
S11a 앵커에는 `t=…ms` 가 없어 그 시험을 재현할 수 없다.
차이는 로그 한 줄의 형식뿐이고 측정·연산 경로는 같다.

### 통과한 완료조건
- 9.11시간 연속 가동 중 **I2C 끊김 없음** (1Hz 로그가 끝까지 유지)
- `t=…ms` 가 정확히 1000ms 간격 — 시계로 쓸 수 있음이 실측 확인됨
- 방전 전 구간에서 vpack/vsys/shunt/Current 레지스터 **상호 일치 유지**
- 8.4V 근방(팩 BMS 차단 직전)까지 오동작 없음
